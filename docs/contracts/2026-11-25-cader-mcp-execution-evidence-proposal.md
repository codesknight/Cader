# Cader → AutoCAD-MCP：执行与观测证据协同建议

日期：2026-11-25。来源：用户明确允许给 MCP 提开发建议；关联 Cader REQ-046 / [#20](https://github.com/codesknight/Cader/issues/20)。状态：建议及验收条件，不是已发布的新协议，不授权改动相邻工作区未提交文件。

## 已有能力与范围

只读核对本地 MCP `05aec6bbd7ac2def6798a6356280324f70b75055`，并通过 GitHub 确认 [PR42 已合并](https://github.com/codesknight/AutoCAD-MCP/pull/42)。已有 [新建图原生证据工作项41](https://github.com/codesknight/AutoCAD-MCP/issues/41)、[截图恢复工作项43](https://github.com/codesknight/AutoCAD-MCP/issues/43)，不把本建议当作从零实现这些功能。

- `managed_server.py` 及 HTTP Bridge 有 instance/document/revision、get_job_status、批处理、分页、save/reopen 等能力；普通 COM 后端能力范围不同。
- 普通截图已有 `autocad-capture/1` 回执、请求关联、打印状态恢复与临时资源清理证据，应扩展现有能力声明和回执。
- Cader 本原稿通过使用普通 COM 动态工具；独立 DWG 只读重开由本次额外验证驱动，不是当前默认每次保存必经。
- 服务应继续独立；不重做 AgentLoop，不在 MCP 定义用户需求、决定源图真值或替用户回答歧义。

## P0：后端能力矩阵及统一身份

建议 `get_backend_status`/已有能力响应准确声明各功能、版本及保证范围：权威 revision、手工修改跟踪、只读重开、截图坐标映射、原生事务、结果对账及保留窗口。COM 不支持的字段明确 unsupported/null；不从 HTTP 的 schema 名称推断 COM 也支持。

文档名称/路径会变，不能单独做写目标身份。对齐已有 instance/document 生命周期 ID，区分工作绑定与只读验收绑定；实体标识按 document 作用域，可增加原生 Handle，但不能跨数据库把 ObjectID 当全局身份。重开或同 hash 副本产生新文档绑定，比较规范化几何/文件hash，不要求原生 ObjectID 恒定。

若只能提供本服务写操作计数，应声明其作用域；没有观察到 AutoCAD 用户手工修改的计数不能标成权威数据库 revision。

验收：两张同名图、SaveAs 改名、用户切换/手工编辑、只读重开、程序重启/后端重连均不能误绑。现有旧工具调用兼容或显式版本选择，不静默切换后端。

## P0：复用现有请求关联，补齐可对账的执行阶段

沿用现有请求/作业机制区分：参数拒绝、未调用原生、派发中、原生已ACK、观测失败、结果未知。返回匹配 request、operation、instance/document 的结构化结果和本次产生/修改/删除实体集合；重复ID冲突、查询保留窗口明确。

- 已 ACK 后查询失败，不应混同于原生执行结果未知。
- 无 ACK 的写超时不能从异常文字、实体数不变或 `JOB_NOT_FOUND` 推断未执行。
- 返回相同/其他 request_id、旧文档证据或不完整回执，Cader 仍保守阻断。
- 对账是只读查询原请求状态，不自动重新提交写入。跨实例/保留窗口外不能虚构“可以安全重放”。

这不是要求普通 COM 立即获得 HTTP journal 的全部保证；先准确声明能力及不可恢复原因，再分阶段补齐。

验收：执行前异常、调用后丢 ACK、ACK 后忙拒绝、延迟完成、进程重启、作业查无记录、错请求/文档回包。都需原生故障注入及实际 CAD 证据，不能仅测字符串 DTO。

## P1：截图证据与可靠的候选实体定位

现有回执保留；建议在能力支持时关联文档身份、capture 前后 revision/规范化几何摘要、实际文件 hash、坐标系、视图/打印范围、DPI、旋转/裁剪、投影信息。后台状态变化后明确旧图失效。

仅平面正交场景可在校准后返回像素↔CAD变换；透视/三维/布局视口另行声明，不能用图宽高推一个假 affine。可结合窗口/包围盒查询返回候选实体，但视觉建议修改前仍需原生实体查询验证。

验收：已知 CAD 校准点在原始 PNG 的像素位置可复算，变换反算误差有明确界限；覆盖 pan/zoom、旋转、DPI、截图裁边及并发人工编辑。校准不成立返回 unavailable，不能从置信度高推断映射正确。截图失败继续保留恢复/清理证据，不能改写旧 unknown。

## P1：字段投影/增量查询与批次语义

复用已有分页接口和实际 backend 能力：增加 fields 投影、affected entity 查询；若支持权威 revision 再考虑 since_revision。分页须在同一观察快照/revision内，变更时显式失效，不拼接来自不同图纸状态的页面。

普通 COM 无原生批事务时只能声明可靠串行、逐项结果和 stop-on-failure。HTTP 原子批处理已有自己的操作范围；managed专用profile和普通HTTP工具的范围亦不同。不能把两者强说相同，更不能把保存文件算作实体事务回滚。

验收：部分批次成功后下一项拒绝，精确返回已提交和未派发项；查询支持字段不足必须明示。日志/模型上下文减少，但独立验收仍拿到必要几何，不能用计数或空数组替代。

## P1：保存与只读重开保证的普通路径对齐

优先复用现有 save/reopen 工具及 artifact 身份/哈希设计。普通路径若补齐同等能力，应显式绑定输出文件、原文档和独立只读验收文档，保护原图及其他打开图纸；返回实际读取到的规范化实体/文件信息。

验收：文件头和hash、同hash只读副本实际可打开、实体/文本比对、其他图纸和打印状态未变；重开失败只能判文件验收未过，不能据此猜测原保存是否未执行。

## Cader 自己负责什么

源图器件/文字/连接解读、事实决议与用户确认去重、主动提问、摘要/上下文续接、验收清单、任务权限与成本预算由 Cader 负责。Vision 对同一标注反复存疑不能要求 MCP 通过“新增OCR工具”兜底；MCP 提供的是实际 CAD 观测与可验证映射。

## 联合验收与交付

1. 在既有协议/能力入口上对齐各后端支持矩阵与正反例，不另建大协议框架。
2. 合成/无CAD测试只证明结构与错误路径；真实COM和HTTP（若选择）分别记录，不能相互替代。
3. 用原始复杂手稿及已有房子/红屋顶蓝墙/大树两类任务联合回归；真实模型自主选择工具，保留原图/原执行证据，不改用简单圆形。
4. 覆盖真实无ACK、查询忙、人工切图/改图、截图恢复失败、保存和只读重开，并保存请求关联、版本、失败与恢复轨迹。
5. Cader 必要条件仍由独立 verifier 判断；unknown不自动重放，人工确认源图不能解除写屏障。

协同建议已提交为 [AutoCAD-MCP #44](https://github.com/codesknight/AutoCAD-MCP/issues/44)，保持 open，等待按后端对齐与联合验收。本文仅建议；本轮未修改独立 MCP 源码、未运行新的真实 CAD/付费模型测试。
